# Shared faculty pages with Drupal-backed academic offers

The implementation connects the seven faculty routes to one Server Component template, resolves each published faculty from Drupal without hardcoded UUIDs, and passes only serializable faculty and program data across the Server/Client boundary. It reuses the homepage faculty image source, groups the filtered academic offer into levels, limits each tab to four cards, and places the existing news section after the offer. Lint and the static build both pass, and the generated Ingeniería page confirms Drupal content, exact faculty and level query parameters, and the expected section order. **Watch for:** **confirmed** the hero renders `Facultad Facultad de Ingeniería`, **confirmed** each route produces nested `<main>` elements, and **confirmed** inactive tab buttons reference tab panels that are not present in the DOM.

**Verdict**: NEEDS_CHANGES

## High-level view

The Drupal integration is server-only and uses the published collection with the faculty image included. Slug matching prioritizes the Drupal alias and falls back to normalized title variants, which supports the seven folder slugs without embedding UUIDs; the client receives only the title, image data, and already-filtered program DTOs.

The academic offer filters programs by normalized faculty and groups only non-empty levels in the requested order. The generated static output confirms that the faculty and level filters are preserved in `Ver más`, while `NewsSection` remains after the offer.

The presentation has three accessibility and semantics defects in the shared template. The visible title duplicates the Drupal prefix, the page adds a second main landmark inside the root layout, and the tab relationship is incomplete while inactive panels are omitted.

<summary>Details</summary>

### Drupal resolution and the Server/Client contract

`services/facultades.ts` remains server-only and requests `node--facultades` with `filter[status]=1` and `field_imagen_facultad`. `getFacultyBySlug` compares the normalized alias first, then the complete title, then a title with the institutional connector words removed. The seven route files supply only their folder slugs, and no UUID is embedded in the implementation.

`FacultyPage` resolves the faculty, offer, and news in parallel. It passes `FacultyAcademicData`, `AcademicLevel[]`, and reduced `FacultyProgram` objects to the client component rather than the Drupal client, contact attributes, or server functions. Program links are normalized by the existing offer service, which accepts only HTTP(S) URLs; the faculty image and alt text continue to come from the same Drupal faculty mapper used by the homepage.

### Faculty filtering, levels, and static export

The server filters programs by `slugFiltro(program.facultad) === slugFiltro(faculty.title)`, then groups only levels with at least one matching program. `nivelFiltro` maps the known levels to the exact catalog labels, so the generated `Ver más` URL uses `facultad=facultad-de-ingenieria&nivel=pregrado`, matching the catalog’s query-string contract. The client renders at most four cards and shows `Ver más` only when the selected level has more than four programs.

The independent `npm run build` completed successfully and listed all seven faculty routes as static pages. Its generated Ingeniería HTML exposes the duplicate heading and nested main landmark described above. `npm run lint` completed with no errors and retained nine warnings in pre-existing header and footer files.

### Hero semantics and title construction

The hero currently constructs its heading as:

```tsx
<h1 className={styles.heroTitle}>Facultad {faculty.title}</h1>
```

The verified Drupal record supplies `faculty.title` as `Facultad de Ingeniería`, so the static result is `Facultad Facultad de Ingeniería`. The metadata helper already handles this prefix conditionally; the hero should use the same normalization or render the Drupal title directly.

The route component is rendered inside the root layout’s `<main>`, but `FacultyPage` also returns `<main>` in both its normal and unavailable branches. This is a concrete landmark violation in the generated document, not a stylistic concern.

### Accessible level tabs

The level buttons have `role="tab"`, `aria-selected`, `aria-controls`, and keyboard-focusable native button behavior. However, the component renders one `role="tabpanel"` for `selectedLevel` only. For example, the inactive `faculty-tab-facultad-de-ingenieria-especializacion` points to `faculty-panel-facultad-de-ingenieria-especializacion` while that panel does not exist until the tab is activated. Rendering each panel and applying `hidden` to inactive panels would preserve the current visual behavior while keeping the ARIA relationships valid.

### Failure states and verification scope

The FEAT evidence records lint/build success and static output inspection, but it does not include an automated or manual assertion for the hero’s accessible structure or the tab-panel references; those checks should be added to the verification after the shared component is corrected.
